# 2026-10-08: F38 recovery loop — repair decisions

The orchestrator crash-looped every two minutes from 2026-10-08 13:46 UTC
onward: `RuntimeError: push failed: HEAD -> unit/F38 (non-fast-forward)`.
This note records the root cause, the repair and the dispositions chosen, as
`AGENTS.md` requires. No scope, roadmap, architecture, feature or unit ID
changes; no acceptance criterion is weakened.

## Root cause

`cycle()` called `recover_branch()` for every `todo` unit with a recorded
attempt. For F38 that reached `push_and_open_pr()`, which ran a plain
non-fast-forward `git push` of the worktree HEAD over `unit/F38` and raised a
bare `RuntimeError` when the remote refused it. The exception escaped
`recover_branch()`, escaped `cycle()` and exited the systemd unit non-zero;
`Restart=always` with `RestartSec=120` then repeated the same failure forever
(restart counter 1360 at inspection). The STOP file was absent, so nothing
halted the loop.

Three defects combined:

1. **Divergence was not checked.** The local worktree held 4 commits the remote
   did not (F37's merge, the F38 replay work rebased onto it, and a duplicate
   `ErrStore` redeclaration removed) while the remote held 1 commit the local
   worktree did not. Recovery pushed anyway instead of detecting that only a
   force-push could publish it.
2. **An existing PR was ignored.** PR #66 already existed for `unit/F38`, but
   the runtime unit carried `pr: 0`, and recovery trusted that counter instead
   of asking GitHub. It therefore tried to open a second PR.
3. **Success was recorded before it happened.** `record_history(unit,
   "recovered")` ran *before* the push, so `history.json` recorded a recovery
   that never occurred.

## Repair (this change)

- `RecoveryConflict(RuntimeError)` — a named, unit-scoped, *expected* Git
  recovery failure. `cycle()` catches **only** this class; `IntegrityError`,
  accounting faults and unexpected programming errors still propagate, so state
  corruption is never hidden behind a blanket handler.
- `validate_recovery_worktree()` compares the reused worktree's branch and HEAD
  with the remote before recovery uses it, and refuses a checkout that still
  holds unfinished local edits (they are preserved, never pushed over). An
  identical or strictly-behind worktree is accepted (behind is fast-forwarded,
  losing nothing); a *diverged* worktree is joined with the remote by an
  ordinary merge commit, so the later push is a normal fast-forward. A merge
  that actually conflicts aborts and raises `RecoveryConflict`; a merge that
  fails for any other reason (a local Git error, not a content conflict) is not
  this unit's fault and surfaces instead of parking it. A force-push is never
  attempted and no history is dropped. The dirty-checkout and both-histories
  protections are the useful overlapping part of the unmerged maintenance-C
  candidate (PR #87), incorporated here explicitly rather than deployed from
  that branch.
- `find_existing_pr()` asks GitHub for the open PR on the branch; recovery and
  `push_and_open_pr()` reuse it instead of creating a duplicate. A recorded
  runtime PR number is reused only when GitHub confirms it *is* the open PR for
  that branch; a stale, closed or foreign number raises `RecoveryConflict`, and
  a GitHub outage raises `DeliveryUnavailable`, so a provider failure keeps its
  backoff/accounting policy and is never mistaken for "no PR exists".
- Recovery records success only after the branch is consistent with its remote
  **and** the PR is known, and it publishes a reconciled head (ahead or merged)
  before reusing the PR, so a fast-forward or a diverged-history merge is never
  left local-only.
- `recover_units()` records the conflict reason, parks only that unit (so it is
  not re-recovered every tick) and lets unrelated eligible units continue.
  Attempt and token counters are untouched; caps, STOP, protected paths, the
  quality gate and independent review are unchanged.
- `adopt_branch_unit()` resolves the ordinary `unit/<id>` branch name and asks
  GitHub whether a merged PR exists for it, then re-checks that the returned
  PR's head branch is exactly the unit's branch before adopting. A merged PR is
  still reported under its head branch after GitHub deletes that branch, so
  branch absence is never read as "no merged delivery"; a unit already merged in
  Git is adopted, never rebuilt. `dispatch()` re-checks a delivery locally
  (`merge-base --is-ancestor origin/<branch> origin/main`) before building, so a
  unit already merged in Git is adopted or parked, and queues a unit that
  already has an open PR instead of building a duplicate; the merge queue then
  re-runs the rebase, `scripts/check.sh`, the quality gate and independent review
  on the exact head, so routing an existing delivery through it bypasses no gate.
- Provider failures keep their existing backoff/accounting policy; they are not
  reclassified as unit failures. A rejected push is a confirmed Git conflict
  (`RecoveryConflict`), but a failed `gh pr create` or PR lookup is a provider
  outage and defers the cycle (`DeliveryUnavailable`).

## F38 disposition

Both histories are preserved and the branch is reconciled. `unit/F38` was
fast-forwarded from `4896fe5` to the merge commit `ad6705c`, whose parents are
the local rebased branch `ac82408` and the remote `4896fe5`. The merge changes
no content: the local branch already contained the remote's replay work,
rebased onto the F37 merge and with a duplicate `ErrStore` declaration removed,
so nothing was duplicated and no unrelated work was introduced. No force-push,
no branch deletion and no history was discarded; the pre-repair heads are kept
as `refs/backup/f38-recovery/*` and as bundles.

Runtime F38 is associated with its verified existing PR #66 and is **not**
marked merged. Its quality finding ("tests do not exercise the change") is
preserved. F38's branch still conflicts with `origin/main` on
`internal/staff/replay.go`, which already carries the F38-a replay store that
was merged separately; choosing between the two implementations is an
architecture decision and is not made here. F38 is therefore parked with that
recovery-conflict reason rather than retried.

## Safest-option choices

- The repair is based on `origin/main`, the accepted integration head, so the
  review diff is the recovery fix alone.
- The live deployed tree carries local `ops/orchestrator.py` edits; they are
  backed up before deployment and re-applied by the normal deploy step.
- No review or protection gate is bypassed; the repair waits for an independent
  review from a different model family before it is merged or deployed.
