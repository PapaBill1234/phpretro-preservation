# Decisions

- **Coordinator:** `gpt-6.1-sol` through A6API. A6API merchant telemetry is authoritative for the model actually used. If Codex displays `gpt-6-sol` while A6API reports `gpt-6.1-sol`, treat that as a Codex display/configuration glitch and record both labels in the run log; do not infer the billed model from the local label.
- **Subagents:** `gpt-6-luna` through A6API for bounded, Sol-approved units only.
- **Jev:** use the existing `jev_judge` MCP tool for typed rankings/classifications over facts already found; batch related questions. The current Codex configuration exposes both `jev_judge` and `jev_gate`, and the global `PreToolUse` hook invokes the Jev gate command. This observed configuration is recorded here; it is not a substitute for testing the hook in a live session.
- **Evidence:** deterministic search/reduction precedes Jev for broad multi-file and noisy-log tasks. Jev receives sanitized candidate IDs and bounded excerpts only.
- **Confidence:** 0.80 permits a verified low-risk selection; 0.60-0.79 requires expanded Sol review; below 0.60, escalation, unavailable Jev, or source disagreement falls back to Sol.
- **Delegation:** no Luna for exact lookups or tiny edits; delegate only bounded units whose expected work can repay a second context.
- **Authority:** Sol verifies every Jev result against source before delegation or acceptance. Jev and Luna never make final authentication, authorization, schema ownership, merge, or runner-security decisions.
- **Economics:** record A6API usage and compare matched Sol-only versus Jev/Luna runs by cost per accepted unit before claiming savings.
- **Foundation status:** supervised only until repository policy, queue, token caps, and evidence transfer are approved.
- **Repository authority:** `https://github.com/PapaBill1234/phpretro-preservation`; `main` is the reviewed milestone branch and the durable Kanban board is `phpretro-preservation`.
- **Current operating model:** the six live profiles are `coordinator` (Sol), `backend` (Luna), `frontend` (Luna), `reviewer` (Sol), `visual` (Luna), and `approver` (Sol). Kanban cards, not ad-hoc sessions, are the default implementation dispatch path.
- **Go security:** the planned foundation must run `go test`, `go test -race`, `govulncheck ./...`, and direct/transitive license inventory after `go.mod` is introduced.
- **A6API evidence:** raw JSONL exports and the Tampermonkey/PowerShell collectors are measurement evidence only. Savings require a matched Sol-only versus Jev/Luna comparison after ten accepted units.
- **F0 baseline:** `go.mod` and `.go-version` now define a dependency-free executable foundation. No product route, schema, or credential is included.
- **External verification:** GitHub branch protection/rulesets, CI execution, and repository settings require verification through an authenticated GitHub review before unattended work.
- **Foundation caps:** F0 is capped at 40,000 uncached input tokens, 20,000 cached-input tokens, 8,000 output tokens, and 45 minutes wall time. F1-F5 are each capped at 60,000 uncached input tokens, 40,000 cached-input tokens, 12,000 output tokens, and 90 minutes wall time. The supervised foundation batch is capped at 340,000 uncached input tokens, 220,000 cached-input tokens, 68,000 output tokens, and ten hours wall time. These are hard stops, not spending targets.
- **F1 provisional cap:** F1 uses 60,000 uncached input tokens, 40,000 cached-input tokens, 12,000 output tokens, and 90 minutes wall time. This is provisional because earlier session/Jev exports do not isolate a reliable F1 usage row; replace it only with measured evidence before changing the cap.
- **Toolchain security:** Go 1.25.13 is the pinned toolchain because CI `govulncheck` identified standard-library fixes beginning at Go 1.25.8/1.25.11/1.25.13. Toolchain changes are reviewed as separate maintenance units before feature work resumes.
- **A6API monitoring:** use the checked-in collectors, raw JSONL archive, rate table, cost report, and archive summaries to track usage and cost per accepted unit. Stop on an actual provider payment/quota/auth failure. No fixed balance floor is required; a user may add an explicit spending cap later.
- **Deferred items:** payments, emulator writes, client handoff, staff operations, Pixel63, Atom, nginx, metrics, fuzzing, and SWF are not authorized by any current grant; each needs its own bounded card with exact scope, evidence, independent review, and a delegated approver verdict. There is no production environment to register or enable, so no production gate applies.
- **Frontend/cache correction:** React is the required frontend and all supported themes must be implemented as versioned React theme packages behind typed Go API contracts. Redis is a required supporting service for approved cache/session-support workloads; MariaDB remains authoritative. Redis usage requires documented namespaces, TTLs, serialization, invalidation, outage behavior, and tests. This supersedes the older draft language that deferred React and Redis as technologies.
- **Localization/CMS correction:** Localization is a first-class capability managed from authenticated React housekeeping. Housekeeping uses the same theme architecture with a dedicated housekeeping style and manages locale catalogs, translations, new button pages, navigation/buttons, website-owned content, presentation-only theme settings, safe media metadata, status/maintenance settings, cache invalidation, and audit history through bounded slices. All mutations require server-side authorization, CSRF, validation, prepared SQL, same-transaction audit, and publication/rollback tests; PolarIS ownership remains unchanged.
- **GitHub merge authority:** the owner explicitly authorized Sol to merge reviewed pull requests through the GitHub API. `main` keeps pull requests, required `foundation` CI, conversation resolution, administrator enforcement, and force-push/deletion protections; it uses zero required approving reviews for this single-operator workflow. The policy and each merge must be documented.
- **Historical queue approval (F8 checkpoint):** F0-F7 were accepted or merged through PR #20; F8 localization contract was the active bounded unit. Later CMS/housekeeping mutations required separate briefs and evidence; current F18-F30 development eligibility below does not waive those exact-unit requirements.
- **User authorization:** the user authorized completing the GitHub setup and remaining readiness work on 2026-10-01; this authorizes the supervised F0-F5 setup batch, not bypassing any security gate.
- **Historical foundation completion:** F0-F5 are accepted on `main` through PRs #1-#18. F3 profile, F4 golden comparator, and F5 content read use synthetic tests and remain read-only. That foundation grant authorized no payments, emulator writes, client handoff, staff operations, Pixel63, Atom, Redis/nginx/metrics/fuzzing, or SWF work; subsequent bounded grants, including the development-only decision below, govern later scope.
- **Foundation economics:** the required local tests passed in `golang:1.25.13`; exact per-unit A6API input/cached/output telemetry was unavailable in the local session and Jev escalated unavailable backend. No cost-savings claim is made until matched telemetry exists.
- **Nerve supervision:** Hermes Nerve `0.3.0` is enabled. It supervises active Kanban worker runs through lifecycle hooks and uses Jev as the default Reflex backend subject to ROI, cooldown, evidence, and fail-open policy. It does not call Jev continuously while the board is idle and does not replace Sol's final authority.
- **Kanban dispatch:** the gateway dispatcher owns claims, worktree isolation, retries, heartbeats, review routing, and terminal state. Workers are bounded by card scope and may not mutate board state outside the native lifecycle tools.
- **Migration status:** the former Sol-plus-optional-Luna prose is historical where retained in draft documents; this file, `AGENTS.md`, `docs/ai-run-state.md`, and `tasks/queue.md` define the current six-profile Kanban approach.
- **Continuation invariant:** every coordinator card must create the next source-backed implementation/review cards and a successor planning card before completing, unless authorized scope is exhausted or a documented stop condition applies. An empty board without an evidence-backed stop record is a failure state to report and repair.
- **2026-10-04 historical route-evidence authorization:*** after the independently accepted F14 evidence/test candidate is delivered to `main`, the user authorizes F15 public-route source evidence and synthetic tests, then successive first-release route evidence/test units when each is source-backed and separately scoped. This evidence-only grant authorizes no schema, credential, real-data, security, or runner change; it does not restrict the separate development-only grant below. Coordinator cards must link an independent review and a successor within their exact boundary, or document the exact stop condition.

The earlier F16 hard stop on unavailable raw response details was re-evaluated after the original disposable Stage 3 container's retained public login body and headers were extracted read-only and verified against the accepted F4 login hash, source manifest, and local capture manifest. Separate development eligibility below does not expand the historical F16 slice. The raw files stay local.
- **2026-10-04 delegated scope approval:** the owner is not a programmer and has delegated bounded development-scope and routine technical gate decisions to a sixth live profile, `approver` (Sol, A6API, `custom:a6api`). The approver reads the exact current repository policy, source evidence, card, candidate commit, independent review result, required CI, and PR, then records one explicit APPROVE, REJECT, or NEEDS_EVIDENCE verdict on the board and the relevant PR, naming the exact SHA, approved unit IDs and paths, an explicit not-approved list, verified facts with identifiers, retained unknowns, remaining gates, and evidence gaps. Board card `t_309369cf` was the first decision under this delegation and the F18-F24 scope gate on PR #31 (`t_d77c8293`) depended on it. The approver never authors, reviews, or merges a change it approves. Its verdict grants no merge or runner/ruleset authority; technical schema, authentication/session and security ownership stays with the coordinator. The former owner-gated development closed list is superseded by the development-only decision below, not by an approver verdict; real credentials/key material, real data and live outside systems remain closed, and there is no production environment to gate. Payments, emulator writes, client handoff, staff operations and other deferred items receive no blanket grant. Approval of a roadmap proposal permits planning and per-unit card creation only where the proposal's own text keeps implementation separately gated; every implementation unit still needs its own exact base, paths, evidence, tests, cap, stop conditions, and independent review, and the coordinator still merges under the reviewed-PR authority above. A changed candidate SHA always invalidates prior CI: exact-head CI must rerun. It also invalidates prior review and approval for code candidates and for prose changes, except a byte-identical prose-only rebase whose full-changed-path content digest is verified by CI or the reviewer profile under Option A below; the coordinator never computes that approval digest. The approver's procedure is the `phpretro-scope-approval` skill; a card must pin it.

- **2026-10-04 development-only project status (owner decision):** this is a development-only project. There is no production deployment, no real user data, and no payments; everything runs against synthetic or disposable data in development environments. The previously closed list is now **open for development use**: authentication, sessions, cookies, CSRF, audit-event design, schema and migrations, and every unit that depends on them may be planned, implemented, tested, and reviewed under the normal card, review, and CI gates. There is no production environment and no production gate, and nothing in this entry defers to a future production decision; real credentials, real user data, and live outside systems remain out of scope. This supersedes the closed-list wording recorded earlier in this file and in `AGENTS.md`.
- **2026-10-04 standing owner instruction:** the owner will not give approvals, answer questions, or unblock anything. Agents must never wait on the owner and never message the owner for a decision; problems are fixed by the agents and the board keeps moving. No card may be parked as "blocked on owner". A blocked card is a defect to repair, not a state to report.
- **2026-10-04 model and chain policy (owner instruction):** `deepseek-v4.1-flash` carries routine work: watchdog and polling, state digests, CI and diff-verification checks, brief-writing, F31-F60 design synthesis, first-pass PR review, and the `backend`, `frontend` and `visual` workers. `gpt-6.1-sol` is reserved for exactly three uses: escalated review (authentication, session or schema diffs, diffs over 400 lines, or a flagged concern), one escalation attempt after two failures on the cheaper model, and design synthesis for units whose scope is unclear (for example F28 and F30). A reviewer must never share the model family of the candidate's author, so a `deepseek-v4.1-flash` candidate is reviewed on `gpt-6.1-sol` and vice versa. A routine unit is one worker card that writes the tests first, implements, runs the checks, opens the PR and performs the first-pass review as a step inside the same card; CI auto-merges on green, the worker creates its own successor from `depends_on`, and workers read one generated digest instead of re-reading the policy files. The `approver` is used only for scope changes. `AGENTS.md`, `CLAUDE.md`, `SOUL.md`, skills and templates are edited only on the coordinator surface. A six-hourly digest writes tokens per role and per delivered unit, cards per delivered unit, and escalation counts to `tasks/queue.md`, recording `unavailable` rather than estimating. Until PR #35 delivers, nothing else merges to `main`.
- **2026-10-04 delegated scope approval (owner decision):** scope approval is delegated to the `approver` profile as recorded by PR #34. The owner confirmed the delegation in a comment on PR #31.
- **2026-10-04 approval stability, Option A (owner decision):** approval binds to a content digest over the candidate's full changed path set rather than to the commit SHA. A pure rebase whose diff is byte-identical may skip re-review and re-approval; the digest comparison runs in CI or on the `reviewer` profile and **never** on the `coordinator`. There is no standing freeze on `main`. This applies to prose-only and documentation-only candidates and is not extended to code yet.
- **2026-10-04 scope eligibility (owner decision):** F18-F30 are all eligible for planning and implementation. They are built in dependency order, one unit at a time, and each unit declares its exact paths, tests, cost cap, and independent reviewer before it starts. Batch B (F25-F30) no longer requires separate owner expansion.
- **2026-10-04 problem escalation (owner decision):** when a unit fails, agents resolve it in this order: (a) retry with a different approach; (b) narrow the unit to the part that works; (c) obtain a second independent reviewer or a different model; (d) split the unit, or move to the next unit and return later. The board must never stall on one unit.
- **2026-10-04 standing limits (owner decision):** three limits remain in force and need no input. Never commit secrets, real credentials, or key material; use obvious development placeholders and environment variables. Do not touch live outside systems, including the original sites and third-party services; work only from disposable captures and local fixtures. Do not weaken the project's own gates: changes to review, CI, branch protection, or approval rules go through a normal reviewed PR with independent review and approval.
- **2026-10-04 evidence rules (owner decision):** never invent expected responses or hashes. Where a capture is missing, build from disposable fixtures and label the unit's fidelity limit in its documentation. The capture stop `t_aed9f2eb` is a fidelity note, not a reason to stop work on other units.
- **2026-10-04 unit budget and reporting (owner decision):** each unit is capped at 3,000,000 tokens across all gates. A unit that reaches the cap is cut down to what is already accepted, merged if it passes review, and the board moves on; the cap is not raised on request. A short plain-English status is written to the queue file when a unit starts, finishes, or is cut down, including token usage per gate. Status is not messaged to the owner.
