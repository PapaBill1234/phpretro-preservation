# F7: React theme contract and Redis support boundary

Status: ready for implementation.

## Base and exact scope

- Base SHA: `d60186af8621ac9211070b860a8d71c2d0ad0741` plus accepted F6 working-tree changes.
- Allowed files: `tasks/F7.md`, `docs/evidence/F7-react-redis-contract.md`, `frontend/**`, `internal/cache/**`, and `tests/**` limited to F7 tests/fixtures.
- Do not connect to production, read real user data, add production credentials, implement theme publishing, implement client handoff, or alter PolarIS-owned tables.

## Deliverable

Create the first React frontend/theme boundary and Redis support contract without pretending to provide product parity yet:

1. Add a minimal package-managed React frontend with a typed, versioned theme manifest and a PHPRetro-compatible starter theme shell.
2. Define the Go/API-to-React view-model boundary using synthetic fixtures only. The frontend must not access databases, secrets, sessions, permissions, CSRF state, or audit mechanisms directly.
3. Define a Redis-backed support interface for approved cache/session-support workloads. MariaDB remains authoritative. Document key namespaces, TTLs, serialization, invalidation, outage behavior, and whether each value is cache-only or session-critical.
4. Keep Redis behind an injected interface and provide a deterministic in-memory test double; do not require a live Redis server for unit tests.
5. Add negative tests for malformed theme manifests, unsupported view-model versions, cache-key namespace violations, expiry/serialization failures, and Redis outage behavior.

## Acceptance and tests

- Frontend dependency versions and license metadata are explicit; no unreviewed dependency sprawl.
- React build/typecheck/test commands are reproducible in Docker or the pinned project toolchain.
- Go checks remain green: `gofmt`, `go test ./...`, `go test -race ./...`, and `go vet ./...`.
- Tests prove themes cannot select routes, database ownership, identity, authorization, CSRF, or audit behavior.
- Tests prove Redis is not treated as MariaDB authority and that outage behavior matches the documented policy.
- Evidence records all synthetic fixtures, unknowns, dependency decisions, and exact commands/results.

## Stop conditions

Stop on a need to guess an API schema, access production or real Redis, add an unreviewed dependency, introduce server-rendered theme templates, store authoritative user/account data only in Redis, expand into theme publishing, client handoff, payments, registration, or security-sensitive mutations, or fail the same verification gate twice.
